## 0b. How to generate the image

Build the image prompt from the template below, filling the four bracketed
slots. Send it to the image tool as written — the wording is load-bearing and
has been tuned so the model does not add decoration of its own.

```
A minimalist flat graphic design poster, 1:1 square, for a software engineering
social post. Pure flat vector design — absolutely no photography, no 3D, no
illustration of people or objects, no texture, no gradient, no glow, no shadow.

Background: a single solid very pale [TINT NAME] wash, uniform across the entire
canvas — almost white, just barely tinted.

A single vertical [ACCENT NAME] stripe runs down the extreme left edge of the
canvas, from the very top to the very bottom, about 8 pixels wide, fully
saturated.

Upper left: a small rounded rectangle chip in a slightly deeper [TINT NAME],
containing the short label "[TAG]" in dark [ACCENT NAME] uppercase letters.

Center left, the main headline in large bold near-black sans-serif type, left
aligned, reading exactly:
"[HEADLINE]"

Lower left: "Muhammad Sarmad" in small bold near-black type, and directly beneath
it "@sarmadkung" in smaller grey type.
Lower right: "[SERIES]" in small grey uppercase letters.

Generous empty space. Nothing else on the canvas. Render all text crisply and
spell every word exactly as written. Do not add any words, logos, watermarks,
icons, or decoration that are not listed above.
```

Accent names to use in the `[ACCENT NAME]` slots — always give the model the
word, not the hex, because image models handle named colors far more reliably:

| Pillar | `[TINT NAME]` | `[ACCENT NAME]` | Reference hexes |
| --- | --- | --- | --- |
| Problem solving | `warm cream` | `golden amber` | `#FCF7EC` / `#F0A500` |
| Software engineering | `pale ice blue` | `bright cyan` | `#EDF8FB` / `#00A6C4` |
| AI engineering | `pale lavender` | `vivid violet` | `#F6F3FE` / `#7C4DEF` |
| Building in public | `pale mint` | `bright green` | `#EAF7EE` / `#2EA043` |

Always give the image model the words, never the hex — image models handle named
colours far more reliably than hex codes.

**Rules that keep generated images consistent**

1. Keep `[HEADLINE]` to 8 words or fewer. Long strings are where image models
   start misspelling.
2. Never ask the image model for a code block. It will produce plausible-looking
   nonsense code. If the post needs real code, switch to `VISUAL-HTML`.
3. Never ask for a diagram, chart, or motif glyph. Same reason. `VISUAL-HTML`
   handles those.
4. After generating, read the text in the image back. If any word is misspelled
   or the stripe is missing, regenerate once. If the second attempt is also
   wrong, return `VISUAL-HTML` output instead and say why.
5. Do not vary the prompt's wording between posts. The fixed wording is what
   makes separate posts look related.

## 1. The governing rule

Four pillars must not mean four designs. Four designs means no recognizable

## 1b. Layout routing — the content picks the layout

Do not force content into a layout. Read the content's shape first, then pick
from the library below. The pillar colours never change; only the arrangement
does.

| If the content is… | Use layout | Canvas |
| --- | --- | --- |
| One idea, one claim | `STATEMENT` | 1200×1200 |
| N parallel items (a list of places, patterns, options, mistakes) | `GRID` | 1200×1500 |
| One subject with several named facets (definition, pattern, when to use, real world, cost) | `ANATOMY` | 1200×1150–1500 |
| An ordered process, pipeline, or request path | `FLOW` | 1200×1200 |
| Two things set against each other (before/after, naive/better, A vs B) | `COMPARE` | 1200×1200 |
| One number that is the whole point | `STAT` | 1200×1200 |
| Too much for one page — a full teach-through | `CAROUSEL` | 1080×1350 ×6–10 |

**Build the page as three bands**: a fixed top row (chip + series), a `main`
region with `flex:1` that centres its content in the leftover space, and a
footer pinned with `margin-top:auto`. This is what prevents the single most
common failure — content stacked at the top with a dead band beneath it.

**Canvas height follows the content.** Never leave a large empty band at the
bottom. Set the height so the footer sits just below the last section: roughly
1200 for 2–3 sections, 1350 for 4, 1500 for 5+ or a 3×3 grid. Square is the
floor; 4:5 is the ceiling, because LinkedIn crops taller than that.

### The layouts

**STATEMENT** — the original single-idea card. Chip, ≤8-word headline, one
optional code block, name lockup. Nothing else. Section 4's rules govern it.

**GRID** — a title band across the top, then N equal cards. 4 items → 2×2,
6 → 3×2, 9 → 3×3. Each card carries: a dark header bar with its number and
name, a small diagram built from the block vocabulary below, and one caption
line of 4–8 words. Each card takes the next colour from the rotation; the
pillar accent is used for the title bar and the highlighted title word.

**ANATOMY** — one subject taken apart. Title, one-sentence lede, then labelled
sections in this order, using only the ones the content has: `THE SHAPE` (a
diagram strip), `REACH FOR IT WHEN` (3 bullets), `WHERE IT SHOWS UP` (2–4 named
chips with a sub-line), `COST` (stat tiles). Section labels are small, uppercase,
in the ink colour, each followed by a hairline rule.

**FLOW** — one chain of steps at large scale, with every decisive step in the
hero style. Two orientations:

- *Horizontal* when the chain is ≤5 steps and branches (the agent loop:
  messages → model → text|tool_use → run tool → result). A branch uses `fan`,
  and each branch row carries its own continuation — never run one arrow out of
  a whole fan, or the diagram claims both branches lead to the same place.
- *Vertical* when the chain is 5+ steps and each step needs a sentence (a
  request path: client → timeout → retry → breaker → database). Steps stack on
  the left at a fixed width, annotations sit to their right.

A loop-back is a dashed panel in the tint under the chain, not a curved arrow —
curved arrows across a flex row do not survive rendering.

**COMPARE** — two panels side by side. Left is the naive version on a plain
white panel; right is the better version on the tinted panel with the accent
border. Each carries a small uppercase label, a code block, and a mono badge
for its cost. One shared line underneath states the trade in plain words —
name what was *spent*, not just what was gained.

**STAT** — one very large mono number in the ink colour, with its unit as a
multi-line phrase set beside its baseline, then up to three supporting tiles,
then one closing line. The big number must be something real and checkable.



### Block vocabulary

Every diagram is assembled from these. Do not invent new primitives; combine
these instead.

- `box` — a labelled rounded rectangle. `hero` variant uses the accent border
  and chip fill, and marks the one step that matters.
- `rows` — a stack of 5 short bars standing for an array; the `on` bars are
  tinted to show the active region.
- `arrow` — a short horizontal line with a solid head. Always left to right.
- `fan` — two or three boxes stacked vertically after one arrow, for a branch
  (hit/miss, allow/deny, left/right).
- `chip` — a labelled tile with a smaller grey sub-line, for real-world uses.
- `stat` — a large mono value over a small descriptive line.

Rules: at most 6 blocks in one diagram; every arrow points right or down; never
two hero boxes in one diagram; labels are 1–3 words.

### Colour rotation for multi-item layouts

`GRID` and any layout with more than four coloured parts cycles this list in
order, starting at the pillar's own accent:

`#E8A200` `#0093AE` `#7C4DEF` `#2EA043` `#DC3F44` `#4F46E5` `#D9730D` `#0E8A6E` `#C2298A`

Each colour also has a pale fill for the hero box, mixed as the accent at about
12% over white.

## 4. Content rules for the image itself

1. The image carries **one** idea in **8 words or fewer**. Everything else
   belongs in the post body — the image is read at thumbnail size.
2. Never put a paragraph on an image. If it needs a paragraph, it needs a
   carousel.
3. Code blocks: **6 lines maximum**, JetBrains Mono, 32px. Highlight in accent
   plus `#8B8B93` only — never full multi-color syntax highlighting, which
   destroys the identity.
4. One visual per image: a code block, *or* a diagram, *or* nothing. Never two.
5. Diagrams use primary text for shapes and accent for the one element being
   pointed at. Two colors, no more.
6. No stock photography, no 3D renders, no AI-generated illustration, no emoji
   on the canvas. Emoji belong in the post body if anywhere.
7. No drop shadows, no glows, no glassmorphism, no gradient meshes. Flat, with
   the hairline color for separation.

## 5. Carousel rules

1. 6–10 slides. Below 6 it should have been a single image; above 10 it is an
   article.
2. Slide 1 is the cover: pillar tag, headline, name lockup, nothing else.
3. Slides 2..n−1 each carry exactly one point, with the point as a 56px
   headline at top and supporting detail below.
4. The left-edge accent rule runs on every slide, unbroken.
5. Slide numbers in secondary text, bottom-right, `03 / 08` format.
6. Final slide is a single question or takeaway plus the name lockup. No
   "follow me" graphics, no like-and-share instructions.

## 6. Review checklist

Before returning any image, verify each:

1. Headline is 8 words or fewer and at least 64px.
2. Left-edge accent rule is present and matches the pillar.
3. Accent appears in no more than the four permitted places.
4. Background is `#0D0D0F`; no light variant slipped in.
5. Name lockup is bottom-left, series number bottom-right.
6. Nothing crosses the 80px safe margin.
7. Legible when the image is scaled to 200px wide — check by shrinking it.
8. Code block, if present, is 6 lines or fewer.

Fail any item, regenerate — do not ship with a note about it.
